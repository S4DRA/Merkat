Continuation handoff: the root-level `MERKAT_IMPLEMENTATION_REPORT.md`, `MERKAT_TEST_RESULTS.md` and `MERKAT_PRODUCTION_READINESS.md` supersede this initial implementation report. The evidence below records the earlier 466a2ac pass; the continuation includes additional checks and explicit remaining blockers.

Review date: October 30, 2026. Source baseline: local Phase 6 from October 17. This working copy adds the approved profile, appearance, calendar, security and spending-tab brief. It is a release candidate that still requires staging acceptance. No production release, hosted migration, production account creation or production data changes were performed.

## What was found

The existing project already had substantial account, direct-message, friendship, group and privacy implementations. It uses Next.js App Router, React, Prisma/PostgreSQL and private Supabase Broadcast invalidations. Fastify is a reference test boundary; phone/Matrix code is inactive. The old worker was a placeholder. Calendar/profile destinations contained incomplete product surfaces, and the new calendar, avatar, recovery and spending features needed persistence, authorization and usable screens.

The hosted URL, https://merkat-umber.vercel.app, still serves the earlier Phase 5.5 deployment. Fresh read-only checks found login/register/manifest and liveness responding, with signed-out chats redirecting to login. Those checks establish public availability only. They do not verify current signed-in messaging, production group behavior or any newly implemented feature.

Historical reports list 60 PostgreSQL tests and 53 Chromium tests from the earlier Phase 6 work, with mocked realtime transport. These are historical evidence, not fresh passes for this change.

## Reproduce in a normal development environment

Use Node 22.17 or later Node 22, npm 11 and a private checkout.

```sh
npm ci
npm run build:packages
npm run lint
npm run typecheck
npm run db:validate
npm run test:unit
npm test
npm run build -w @merkat/web -- --webpack
npm run test:ui
npm run build -w @merkat/worker
```

`npm test` provisions isolated PostgreSQL clusters; it must never point at production. The existing full Playwright suite uses its own database and HTTPS test ingress. `npm run test:components` is a supplementary mocked-HTTP component suite. `npm run test:sql:offline` is a Windows-only SQL harness for the installed embedded PostgreSQL binaries. Whole-repository format checking has pre-existing historical formatting debt; format and check the changed source subset for this revision.

`npm run dev:local` creates only its owned loopback database under `artifacts/local-development`, migrates that owned cluster, and starts Next plus the reminder worker. It disables hosted realtime and external push credentials. Register your own local accounts. Local HTTP persistence works without Supabase; live cross-client invalidations need the documented private Supabase setup. This command cannot be exercised inside the current socket-restricted sandbox.

For this sandbox only, `scripts/build-sandbox.ps1` synchronizes real package copies because workspace junction creation is denied. A normal npm workspace install uses links and does not need that helper. The Next build uses `MERKAT_BUILD_DIR`, `MERKAT_BUILD_OUTPUT` and `scripts/sandbox-fs.cjs` only during verification; copied workspaces also require disabling the dependency cache to avoid stale exports. Do not set these overrides or the preload in deployment.

## Staging and release acceptance

1. Create a separate private staging database and app environment. An old preview pointing at production is not staging. Verify a backup/restore plan before any eventual production migration.
2. Run a clean install and the complete real integration/browser suites. Review the seven new migrations after the seven original migrations. Check Prisma migration history and schema drift on staging before proceeding.
3. Configure exact HTTPS APP_ORIGIN, verified database TLS, persistent auth-rate-limit secret and the existing trusted production ingress. Reconfigure Supabase private Broadcast signing/RLS according to the architecture docs. No public subscription fallback is permitted.
4. Start the worker with the same database: build shared packages and `@merkat/worker`, then run `npm start -w @merkat/worker`. Use a process supervisor with restart and log/queue monitoring. PostgreSQL is the durable queue; multiple workers claim jobs using row locks. Alternatively, schedule the Bearer-protected `/api/internal/reminders` endpoint at least every minute with CRON_SECRET for in-app reminders only. Push still requires the worker. Avoid relying on a once-daily scheduler for hour-sensitive reminders.
5. Generate VAPID keys privately (`npx web-push generate-vapid-keys`). Set MERKAT_PUSH_PUBLIC_KEY/PRIVATE_KEY/SUBJECT on web and worker. Never put the private key in NEXT_PUBLIC variables. Browser permission is requested only after an explicit enable action. Test permission denied, expired subscriptions, opt-out, logout, account switching, two devices, foreground/background, deep-link authentication and actual notification display on supported browsers, including a physical Android/Xiaomi device and applicable installed iOS web-app behavior.
6. Create three real staging users. Verify registration without email/phone verification, login/logout/rotation, password change, code generation and one-use recovery, revoked-session rejection, related-profile access, blocked/removed-user denial and avatar persistence across reloads. Upload actual PNG/JPG below/at/above 2 MB, mismatched MIME/signature and oversized dimensions; ensure no private image response is publicly cached.
7. Verify DM/group message persistence, optimistic retry, dedupe, unread/read states, reconnect and cross-client private realtime with two independent browser contexts. Test group invitation, role change, leaving/removal, blocks and private profile/feature access after changes.
8. Create personal/DM/group events; check all calendar views, independent Maybe/subscription, Going automatic subscription, timezone/DST behavior, edit/cancel, native chat references and ICS. Drive 24/5-hour jobs with a staging clock or disposable test events; restart the worker and run duplicate/concurrent cycles. Confirm notifications are unique and no removed/blocked member receives new event content.
9. Reproduce the three-person 1,350 TRY bill. Confirm partial shared consent does not charge anyone, a decline cancels the proposal, equal remainders reconcile, others cannot edit an order, group members cannot close as admins, stale versions/retry payload conflicts are safe, venue payments differ from consumption, repayment requires the recipient, and the closed expense snapshot cannot change. Test own-order edits and overpayment rejection.
10. Review keyboard-only navigation, modal focus, reduced motion, larger text, OS theme switches, 390px/mobile landscape/desktop sizes, long names, empty/loading/failure states and real-device safe areas. Run accessibility automation and a screen-reader review; current component checks do not certify full accessibility.
11. Review observability, retention, database capacity, dependency/security scanning and rollback. Only after the staging gates pass and the owner explicitly authorizes production should production migrations and deployment run. This work does not grant that authorization.
